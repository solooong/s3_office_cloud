# 08. Миграция с Яндекс.Диска

Документ описывает перенос файлов организации из Яндекс.Диска (Яндекс 360) в Cloud
Suite. Миграция выполняется волнами, с контрольными суммами, возможностью
приостановки и откатом. Ответственные: ИТ-администратор (исполнение), владельцы
подразделений (согласование волн), служба безопасности (согласование публичных
ссылок).

## 1. Что переносится и что нет

| Объект Яндекс.Диска | Переносится | Как |
|---|---|---|
| Файлы и папки в «Диске» пользователя | да | rclone copy, содержимое и структура |
| Общие папки («Общие диски»/расшаренные папки) | да, как обычные папки | права пересоздаются в Nextcloud вручную/скриптом |
| Публичные ссылки | нет | пересоздаются в Nextcloud, старые отключаются |
| История версий файлов | нет | переносится только актуальная версия; новые версии начинаются с даты миграции |
| Корзина Яндекс.Диска | нет (по решению заказчика) | восстановление возможно только до отключения аккаунтов |
| Комментарии/подписи к файлам | нет | — |
| Настройки синхронизации клиентов | нет | клиенты перенастраиваются на новый адрес |

Важно: Яндекс.Диск не отдаёт чужие «расшаренные» файлы через API того
пользователя, которому они расшарены, — каждый пользовательский дамп снимается
под учётной записью владельца данных. Поэтому в инвентаризации фиксируется
**владелец** каждой папки.

## 2. Инвентаризация (T-14 дней)

Соберите таблицу `inventory.csv`:

```csv
yandex_login,nextcloud_user,role,quota_bytes_used,quota_bytes_limit,folders_count,shared_folders,public_links
ivanov@example.ru,ivanov,employee,5368709120,21474836480,42,3,2
petrova@example.ru,petrova,department_head,21474836480,53687091200,128,7,5
```

Команды для сбора (rclone remote `yandex` уже настроен, см. п. 3):

```bash
# занятое место и лимит
rclone about yandex: --json | jq .

# размер и число объектов по папкам верхнего уровня
rclone size yandex: --json

# список папок верхнего уровня
rclone lsf yandex: --dirs-only

# файлы с изменением за последние 30 дней (для оценки дельты)
rclone lsf yandex: --recursive --files-only --max-age 30d | wc -l
```

Публичные ссылки Яндекс.Диска через rclone не видны. Их список выгружается вручную
из интерфейса Яндекс.Диска (раздел «Ссылки») или через REST API
`https://cloud-api.yandex.net/v1/disk/public/resources` по известным ключам.
Результат — `public-links.csv`: `owner,url,path,permissions,expires`.
Эти ссылки **не переживут** миграцию: их нужно пересоздать (п. 7) и уведомить
получателей.

## 3. Настройка rclone (Яндекс)

Выполняется на сервере Cloud Suite (или на промежуточной машине с достаточным
диском). Устанавливать rclone нужно на хосте, а не в контейнере.

```bash
sudo apt-get install -y rclone jq
rclone version
```

Настройка remote:

```bash
rclone config
# n) new remote
# name> yandex
# Storage> yandex
# client_id> (оставить пустым — используется встроенный client_id rclone)
# client_secret> (оставить пустым)
# config_type> 1  (автоматическая авторизация через браузер)
# Откроется ссылка — войдите под сервисной учётной записью и разрешите доступ.
# token> (сохранить автоматически)
# y) yes this is OK
```

Дальше добавьте remote’ы для остальных пользователей (по одному на владельца):

```bash
rclone config create yandex_ivanov yandex config_is_local false
rclone config create yandex_petrova yandex config_is_local false
rclone listremotes
```

Требования:

* токены — секреты: файл `~/.config/rclone/rclone.conf` с правами `600`,
  не пересылать в чатах и не коммитить;
* для миграции лучше завести сервисные учётные записи Яндекса с доступом к «Общим
  дискам» организации, чтобы не зависеть от пароля конкретного сотрудника и 2FA;
* rate limits: Яндекс ограничивает частоту запросов. При массовых ошибках
  `429`/`503` уменьшайте параллелизм (`--transfers`, `--checkers`) и
  используйте `--tpslimit`.

Проверка доступа и целостности канала:

```bash
rclone lsd yandex_ivanov: | head
rclone copy yandex_ivanov:test-canary /tmp/canary --checksum -v
rclone check yandex_ivanov:test-canary /tmp/canary --checksum
```

## 4. Сопоставление пользователей

`mapping.csv` — единственный источник истины о том, куда льются данные:

```csv
yandex_remote,yandex_login,nextcloud_user,quota_gb,role
yandex_ivanov,ivanov@example.ru,ivanov,20,employee
yandex_petrova,petrova@example.ru,petrova,50,department_head
yandex_shared,shared@example.ru,shared_docs,200,group
```

Правила:

* `nextcloud_user` должен существовать **до** миграции (создаётся
  `scripts/rbac-sync.sh` по `config/rbac/roles.yaml` или `occ user:add`);
* квота в Nextcloud не меньше `quota_bytes_used` из инвентаризации, иначе
  копирование остановится на середине;
* служебные и уволенные аккаунты: данные переносятся в общий
  `shared_docs` под ответственность подразделения;
* все адреса в mapping — корпоративные, личные аккаунты `@yandex.ru` сотрудников
  мигрируются только по письменному согласованию (персональные данные).

## 5. Тестовая миграция (staging)

До основной миграции один и тот же набор прогоняется на тестовом контуре:

1. создайте тестовую учётную запись `migration-test` с квотой 5 ГБ;
2. скопируйте 2–3 «эталонные» папки (включая глубокую вложенность, кириллические
   имена, файлы >4 ГБ, документы, которые открываются в OnlyOffice);
3. проверьте: число файлов, контрольные суммы, размеры, открытие XLSX/DOCX,
   отображение кириллицы, права после шаринга;
4. измерьте скорость: `rclone copy --progress` показывает throughput. Оцените окно
   финальной дельты: `(объём дельты) / (измеренная скорость)`.

Типичная скорость одного потока Яндекс→сервер — 10–40 МБ/с; при 4 потоках
`--transfers 4` реально получить 30–80 МБ/с в зависимости от канала.

## 6. Миграция

Выполняется скриптом `scripts/migrate-yandex-disk.sh`, который оборачивает rclone:
читает `mapping.csv`, копирует данные в WebDAV целевого пользователя
(`/remote.php/dav/files/&lt;user&gt;/`), сверяет контрольные суммы, пишет
`migration-report.csv` и умеет продолжать с места остановки.

Флаги скрипта:

| Флаг | Назначение |
|---|---|
| `--mapping FILE` | CSV сопоставления (обязателен) |
| `--target-url URL` | базовый URL сервера, по умолчанию `https://$CLOUD_DOMAIN` |
| `--wave N` | разбиение на волны (по умолчанию все пользователи за один прогон) |
| `--dry-run` | показать план (какие remote → какие папки, объём), ничего не копируя |
| `--checksum` | сверка по хешам после копирования |
| `--resume` | продолжить прерванный прогон |
| `--report FILE` | путь к CSV-отчёту |

Порядок:

```bash
# 0) бэкап текущего состояния контура и проверка предусловий
make backup

# 1) план без изменений
./scripts/migrate-yandex-disk.sh --mapping mapping.csv --dry-run

# 2) волна 1 — ИТ-отдел и добровольцы (5–10 человек)
./scripts/migrate-yandex-disk.sh --mapping mapping.csv --wave 1 --checksum --report migration-wave1.csv

# 3) проверка результата по отчёту и выборочно в UI
column -s, -t migration-wave1.csv | head -30
```

После каждой волны — сверка:

```bash
# исходник: размер и количество объектов
rclone size yandex_ivanov: --json
rclone lsf yandex_ivanov: --recursive --files-only | wc -l

# приёмник: пересканировать файлы пользователя в Nextcloud
docker compose exec -T -u www-data app php occ files:scan --path="/ivanov/files"
```

Критерий приёмки волны: количество файлов совпадает (± служебные `.DS_Store`,
`Thumbs.db`, которые удаляются), сумма размеров в пределах 0,1 %, отчёт не содержит
`FAILED`.

Практические ограничения:

* имена: Nextcloud запрещает символы Windows (`* ? " &lt; &gt; | :`) — скрипт
  логирует переименования в отчёт; заранее предупредите владельцев папок;
* пути длиннее 4000 символов и файлы больше `PHP_UPLOAD_LIMIT` (10 ГБ) — отдельный
  список исключений, согласуется индивидуально;
* Яндекс отдаёт только актуальную версию — версии в Nextcloud начинают копиться с
  момента миграции;
* общие папки копируются один раз (во владельца), затем расшариваются в Nextcloud;
  дублирование под каждого участника недопустимо.

## 7. Пересоздание общих папок и публичных ссылок

### 7.1 Общие папки

1. владелец папки даёт доступ группе отдела (или конкретным сотрудникам) — через
   UI или `occ`/OCS;
2. участники получают права «Редактирование» (не «Поделиться» — по политике
   организации, см. [04-rbac-and-sharing.md](04-rbac-and-sharing.md));
3. запишите соответствие в `shares-report.csv`: старая папка → новый путь →
   кому расшарено.

### 7.2 Публичные ссылки

Публичные ссылки Яндекса **не работают** после отключения аккаунта. Для каждой
ссылки из `public-links.csv`:

1. владелец (или ИТ по поручению) создаёт ссылку в Nextcloud с паролем и сроком
   действия (UI или OCS, см. [04-rbac-and-sharing.md](04-rbac-and-sharing.md));
2. пароль передаётся получателю отдельным каналом;
3. получателей старой ссылки уведомляют заранее — за 5 рабочих дней;
4. после cutover старые ссылки Яндекс.Диска отключаются (или аккаунты
   деактивируются) и перестают открываться.

Ссылки «с редактированием» пересоздаются только для получателей, которым это
действительно нужно: редактирование по ссылке — риск, требующий согласования.

## 8. План переключения (cutover)

| Этап | Когда | Действия | Ответственный |
|---|---|---|---|
| T-14 | за 2 недели | инвентаризация, mapping, тестовая миграция | ИТ |
| T-7 | за неделю | волны 1–2 (ИТ, добровольцы), рассылка инструкции пользователям | ИТ + HR |
| T-3 | за 3 дня | волны 3–4 (все отделы), проверка квот и прав | ИТ |
| T-1 | накануне | объявление «режим только чтение в Яндекс.Диске с 18:00», финальная проверка бэкапа | ИТ |
| T-0 18:00 | день X | **заморозка**: запрет записи в Яндекс.Диск, финальная дельта | ИТ |
| T-0 20:00 | | дельта-копирование (`--resume --checksum`), сверка, отчёт | ИТ |
| T-0 21:00 | | пересоздание шар и публичных ссылок, уведомление получателей | ИТ + владельцы |
| T+1 | следующий день | переключение клиентов на `https://cloud.example.com`, старые клиенты отключаются | пользователи + ИТ |
| T+7 | неделя | деактивация аккаунтов Яндекс.Диска, удаление данных у провайдера по регламенту | ИТ + ИБ |
| T+30 | месяц | разбор инцидентов, закрытие проекта | руководитель проекта |

Коммуникация (шаблон):

```text
Тема: Переход на корпоративное облако — с 12 ноября

С 12 ноября файлы хранятся на корпоративном сервере: https://cloud.example.com
Ваши файлы уже перенесены. Что нужно сделать:
1. Войти по ссылке (логин как в почте, пароль придёт отдельно).
2. Установить приложение Nextcloud и указать адрес https://cloud.example.com.
3. Проверить, что все нужные папки на месте (инструкция: docs/10-user-guide.md).
С 12 ноября Яндекс.Диск переводится в режим только чтения, с 19 ноября — отключается.
Вопросы: helpdesk@example.com, тел. ...
```

## 9. Откат

Откат возможен, пока аккаунты Яндекс.Диска не удалены и данные не изменены:

1. приостановить миграцию (`Ctrl+C`, состояние сохраняется для `--resume`);
2. вернуть пользователям доступ к Яндекс.Диску (снять заморозку), объявить об откате;
3. удалить перенесённые данные из Nextcloud, чтобы не было двух версий правды:
   удаление папок владельцем и очистка корзины, затем
   `occ files:scan --all` для синхронизации индекса;
4. разобрать причину (несовпадение квот, ошибки rclone, массовые переименования),
   исправить mapping и повторить волну.

После удаления аккаунтов Яндекса откат невозможен — поэтому удаление выполняется
последним шагом и только после недели стабильной работы.

## 10. Валидация после миграции

- [ ] `migration-report.csv`: все строки `OK`, нет `FAILED`.
- [ ] Число файлов и суммарный размер по каждому пользователю совпадают с инвентаризацией.
- [ ] `occ files:scan --all` завершился без ошибок.
- [ ] Выборочно открыты DOCX/XLSX/PPTX — редактирование и сохранение работают.
- [ ] Кириллические имена и пути отображаются корректно в вебе и в desktop-клиенте.
- [ ] Общие папки доступны участникам, права соответствуют матрице.
- [ ] Публичные ссылки пересозданы, старые отключены, получатели уведомлены.
- [ ] Квоты позволяют работать (нет пользователей на 99 %).
- [ ] Пользователи прошли вход и не сообщают о пропаже файлов (сбор в течение 7 дней).
- [ ] Старые аккаунты Яндекс.Диска деактивированы, отчёт об удалении данных — у ИБ.
